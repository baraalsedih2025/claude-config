# rag-dev-key-gating

- **Recorded**: 2026-09-08
- **Status**: **current state — NOT an accepted risk.** Posture not yet decided.

## Why this file is not an acceptance

`rag.dev.iohealth.com` is internet-reachable and gated by an `X-API-Key` header
match at the proxy. That is **described** here, not endorsed.

The distinction from `bge-m3-public-exposure.md` is the point of splitting them,
and it is not cosmetic:

| | `bge-m3.dev` | `rag.dev` |
|---|---|---|
| Gate | the model server's own key, no proxy check | `X-API-Key` matched per caller **at the proxy** |
| Behind it | a **stateless model** | the **corpus** — pgvector, reranker, cortex |
| Compromise yields | compute | **data** |
| Posture | accepted risk, deliberate, reviewed 2026-12-07 | **undecided** |

The `bge-m3` acceptance rests entirely on the backend being stateless. That
argument does **not** transfer here, because what sits behind `rag.dev` is the
retrieval corpus. Folding the two together would have quietly extended an
acceptance to a service it was never reasoned about.

## What is undecided

These are open questions, not accepted conditions:

- **Is proxy key-matching a sufficient control for a data-bearing service on
  the public internet?** No IP allowlist, no mTLS, no VPN, no per-caller
  identity beyond a shared secret. A shared static header is not
  authentication of a *caller* — anyone holding the string is indistinguishable
  from the intended user.
- **Who are the four keys for?** Until the access logs answer this, the blast
  radius of rotating any of them is unknown, and so is whether any is unused.
- **`RAG_V2_API_KEY` routes to the same backend as `RAG_API_KEY`** — the split
  it existed for has collapsed. Retire it, or restore the distinction?
- **The cortex key lives in the Caddyfile**, not an env file, unlike the other
  three. Inconsistent, and it means the routing config is itself a secret.
- **The legacy service on `:8080` is still serving traffic** after 19+ days.
  Intended, or forgotten?

## What this rules out, pending a decision

- **Do not treat `rag.dev` as covered by the `bge-m3` acceptance.** It is not.
- **Do not rotate any of the four keys** until the access logs identify
  callers. Agreed 2026-09-08: let the logs run at least a week first.
- **Do not add another key or route** to this host before the existing four are
  understood. There are already more keys than known consumers.
- **Do not hand-edit the `rag.dev` Caddyfile block** —
  `configure_dual_rag_route.sh` regenerates it.

## How this file gets closed

It stops being a state record and becomes a decision when someone answers: is
proxy key-gating accepted as the control for this service, or does it need a
network-level control as well?

Either answer is fine and should be recorded with its own review date. What is
not fine is the current state persisting *by default* rather than by choice —
which is exactly the failure mode `bge-m3-public-exposure.md` avoids by
carrying an expiry.
